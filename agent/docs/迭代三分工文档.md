# 迭代三分工文档

> 项目：基于 Agent 的文本可行度评估插件  
> 仓库结构：`agent/agent` 为 Agent 主框架，`agent/backend` 为后端服务，`agent_frontend` 为浏览器插件前端  
> 团队人数：5 人  
> 规划目标：在现有迭代二代码基础上，完成“总结结果、Agent 互相辩论、文章范围缩减到具体领域、对话框、工具扩展、skill 存储和处理、数据库”七项能力

---

## 一、现有代码基础与迭代三切入点

本次分工基于当前仓库的真实实现，而不是从零规划。现有主链路如下：

1. 前端插件从网页提取正文：`agent_frontend/content/content_script.js`
2. 扩展后台转发到本地后端：`agent_frontend/background/service_worker.js`
3. FastAPI 提供 SSE 流式接口：`agent/backend/main.py`
4. Agent 主流程执行 `scan -> plan -> ReAct`：`agent/agent/agent.py`
5. 现有事件模型定义在：`agent/agent/models.py`
6. 现有工具注册表定义在：`agent/agent/tools/registry.py`
7. 现有侧边栏只展示时间轴，不展示总结区与会话区：`agent_frontend/sidepanel/panel.html`、`agent_frontend/sidepanel/panel.js`

### 现有能力

- 已有单 Agent 核查流程
- 已有声明扫描与排序能力
- 已有 4 个工具：
  - `web_search`
  - `wikipedia_lookup`
  - `source_verifier`
  - `cross_reference`
- 已有 SSE 流式事件传输
- 已有时间轴式侧边栏展示

### 当前缺口

- 还没有“总结结果”专用事件和展示区域
- 还没有多 Agent 辩论机制
- 还没有“领域缩减/领域路由”能力
- 还没有插件内对话框
- 还没有面向具体领域的新增工具
- 还没有 skill 的存储、选择、加载、注入机制
- 还没有数据库和历史记录持久化

---

## 二、迭代三目标拆解

本次迭代三将需求拆成 7 个功能包：

### 1. 插件侧边栏添加总结结果

- 在现有 `timeline` 时间轴之外，新增“分析总结”区域
- 汇总错误条数、通过条数、主要问题类型、代表性证据、整体结论
- 后端需要新增 `summary` 类事件，或在 `done` 前推送汇总数据

### 2. 添加 Agent 互相辩论

- 当前 `agent.py` 只有单个 Agent 的 ReAct 循环
- 迭代三需要设计至少两个角色：
  - `Verifier Agent`：负责提出初判
  - `Challenger Agent`：负责反驳、质疑证据充分性
- 最终由 `Judge Agent` 或主控流程汇总结论

### 3. 文章范围缩减到具体领域

- 当前正文抽取后直接整篇进入扫描器
- 需要先做领域分类或主题识别，如：
  - 医学健康
  - 经济金融
  - 科技科普
  - 政策新闻
- 根据领域选择不同 skill、prompt、工具和核查策略

### 4. 添加对话框

- 前端新增会话区，允许用户追问：
  - 为什么判错
  - 证据来自哪里
  - 是否可以重新验证
- 后端需要支持会话上下文和消息存储

### 5. 添加调用工具

- 不是简单重复已有 4 个工具，而是补充“原有代码没有”的领域工具
- 新工具要服务于领域化核查、辩论和对话追问

### 6. skill 存储和处理

- skill 需要具备：
  - 元数据
  - 适用领域
  - prompt 模板
  - 允许调用的工具集合
  - 可选输出格式约束
- skill 既要能被 Agent 加载，也要能被数据库持久化

### 7. 添加数据库

- 保存分析记录、声明、事件流、工具调用、总结、会话消息、skill 配置
- 为前端总结展示、对话恢复、历史记录查询提供支撑

## 三、推荐新增工具清单

以下工具均为现有代码中没有的工具，建议在迭代三优先补充。

| 工具名                                         | 适用领域             | 推荐理由                                                             | 为什么现有工具不够                                                    |
| ---------------------------------------------- | -------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `wikidata_lookup`                              | 通用实体核验         | 可查询结构化实体属性，如出生日期、国籍、机构成立时间、别名、隶属关系 | `wikipedia_lookup` 返回的是搜索摘要，不够结构化，难以稳定核验实体属性 |
| `official_statistics_lookup`                   | 经济、人口、社会统计 | 直接核查统计口径、年份、指标值，适合 GDP、失业率、人口等数字型声明   | `web_search` 搜索结果噪声大，数字声明容易被低质量页面误导             |
| `pubmed_search`                                | 医学健康             | 医疗、药物、疾病、营养、实验结论等声明更适合用论文摘要和期刊证据核实 | 现有工具缺少医学权威来源，容易把通用网页内容当证据                    |
| `openalex_search` 或 `semantic_scholar_search` | 科研、学术           | 适合“研究表明”“论文指出”“实验发现”等内容                             | `wikipedia_lookup` 不适合查具体论文，`web_search` 精度不足            |
| `news_archive_search`                          | 新闻、时政、事件类   | 可验证事件发生时间、地点、参与方和报道一致性                         | `source_verifier` 只能抓单个 URL 正文，不能做多源事件交叉比对         |

### 工具优先级建议

1. `official_statistics_lookup`
2. `wikidata_lookup`
3. `pubmed_search`
4. `openalex_search`
5. `news_archive_search`

### 工具接入原则

- 所有新工具仍沿用 `registry.py` 的统一注册规范
- 工具函数仍保持 `async def tool(input: str) -> str`
- 工具输出必须可被辩论 Agent 和总结模块消费
- 工具调用日志必须写入数据库

## 十、风险与规避方案

### 风险 1：辩论流程复杂，接口频繁变动

规避：

- 第 1 周必须冻结事件结构
- A、B、C 每周至少进行一次接口同步

### 风险 2：工具太多导致实现分散

规避：

- E 先做 3 个高价值工具
- 不追求一次性做全领域

### 风险 3：领域识别不准，导致 skill 选错

规避：

- D 先采用“领域分类 + 回退 general skill”的保守策略
- 无法高置信识别时不强行细分

### 风险 4：前端功能多，侧边栏过于拥挤

规避：

- C 采用分区布局：
  - 顶部总结
  - 中部时间轴
  - 底部对话

### 风险 5：数据库工作量被低估

规避：

- B 首版使用 SQLite
- 优先保证“能查、能恢复、能落库”，后续再考虑复杂优化
